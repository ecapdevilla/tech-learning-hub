Automated System Final Engineering Sprint

Complete, refine, test and document your automated system. Your goal is to prove that the complete flow works: the system senses an input, makes a logical decision and produces an output.

⏱ 2 hours ⚙ Automation 🧪 Testing & Debugging 📘 Technical Documentation

🎯 Learning Objective

Complete and refine the automated system design, simulation or prototype, and technical documentation by applying inputs/sensors, logical decisions, outputs/actuators, testing and debugging.

🧭 Cycle Theme

Complete & Refine the Automated System

Sense → Think → Act → Test → Document

1 · Understand the Engineering Flow

👁️
SENSE · Input

A sensor, button, value or user action provides information to the system.

🧠
THINK · Logic

The system evaluates the input using rules, comparisons or logical operators.

⚙️
ACT · Output

An actuator or interface performs an action: light, sound, movement, message, alarm or other response.

INPUT→PROCESS / LOGIC→OUTPUT→TEST→IMPROVE

2 · Choose Your Development Environment

🔌
Wokwi

Build and test electronic simulations with sensors, actuators and microcontrollers.

🧩
Tinkercad

Design circuits and automation logic in a visual simulation environment.

🌐
HTML + CSS + JavaScript

Create a simple web-based representation that simulates the system input, decision and output.

The platform may change, but the engineering requirement does not: your team must demonstrate a meaningful input, logical processing, an output, testing and clear documentation.

3 · Learn Before You Build

The 3 questions every automated system must answer

1. What does it detect?Motion, light, temperature, distance, water level, a button, a typed value...
2. What decision does it make?IF the value meets a condition, THEN the system chooses an action.
3. What action does it perform?Turn on a light, activate an alarm, move a servo, display a warning or change the interface.

Example A · Physical automation

Problem: a room should alert when motion is detected.

INPUT: PIR motion sensor
LOGIC: IF motion = detected
OUTPUT: LED ON + buzzer ON
TEST 1: no motion → outputs OFF
TEST 2: motion → outputs ON

Example B · HTML simulation

Problem: simulate an automatic temperature alert in a web page.

INPUT: temperature value
LOGIC: IF temperature > 30
OUTPUT: show red alert
ELSE: show normal status

The interface can use:
- number input
- button or automatic event
- status card
- color/message change

4 · Your 2-Hour Engineering Sprint

0–12

Warm-up · Automation Arena

Review sensors, actuators, IF/THEN logic, automation and testing with Code Battle Live.

12–25

System Audit

Identify what is already complete and what is missing: input, logic, output, diagram, tests and documentation.

25–80

Final Build Sprint

Complete and refine the simulation, prototype or web representation. Make the Sense → Think → Act flow visible and functional.

80–102

Testing & Debugging

Test at least three input situations, compare expected vs. actual behavior, fix failures and retest.

102–114

Engineering Documentation

Complete the system diagram, components, input-process-output explanation, logical rule, test evidence and final technical explanation.

114–120

Progress Check & Reflection

What have you completed? What is left? What was the most difficult part of designing the system?

Debug Cycle

1. Observe: What failed?

2. Locate: Input, logic or output?

3. Fix: Change the smallest necessary part.

4. Retest: Run the same case again.

5. Record: What changed and why?

8 · Final Completion Checklist

Engineering Flow

  • Input / sensor identified
  • Logical decision works
  • Output / actuator responds
  • Sense → Think → Act is clear

Functionality

  • Main system flow works
  • No known critical error
  • User/system feedback is clear
  • Reset/recovery works when relevant

Testing

  • 3 or more test cases
  • Expected vs. actual recorded
  • At least one bug analyzed
  • Fix and retest completed

Documentation

  • Purpose explained
  • Components or elements listed
  • Diagram completed
  • Logic explained

Team Understanding

  • Each member can explain the system
  • Team can identify input, logic and output
  • Team can explain one bug/fix
  • Team can describe one improvement

Final Evidence

  • Working simulation/prototype/link
  • Testing evidence ready
  • Technical explanation ready
  • Ready for final review
